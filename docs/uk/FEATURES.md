# Можливості

## Можливості проєкту

### Доступність перевіряється з усіх боків

- Кожне правило axe-core для WCAG 2.2 A та AA, а також його найкращі практики, виконується у відрендереній сторінці, тож виявляються й дефекти, які вносять скрипти.
- Розмітку кожної сторінки, а не вибірки, перевіряють на вади доступності, які html-validate бачить без браузера: відсутні підписи полів, пропущені рівні заголовків, відсутній альтернативний текст.
- Роботу з клавіатури перевіряють на кількох сторінках кожного шаблону: Tab має досягати кожного елемента керування без пасток, фокус має бути видимим і не перекритим, першим має йти посилання для переходу до вмісту, а обробники кліків на звичайних елементах потрапляють у звіт.
- Налаштування відвідувача враховуються: анімації зупиняються за зменшеного руху, текст лишається читабельним у темній схемі й підвищеному контрасті, які пропонує сторінка, фокус і значки не зникають у режимі високої контрастності Windows, а поля форм досить великі, щоб телефони не збільшували масштаб.

### Сторінки з клієнтським рендерингом перевіряються такими, якими їх бачать відвідувачі

- Сторінку, чиї теги, посилання чи вміст з’являються лише після виконання її скриптів, рендерить справжній браузер, тож перевіряється саме те, що бачать пошукові системи та відвідувачі.
- Рендеряться лише розділи, яким потрібен браузер; решта сайту обходиться звичайним HTTP на повній швидкості в тому самому запуску, а розділ, що рендерить свої теги на клієнті, можна виявити автоматично.
- Помилки консолі, час завантаження та кожен ресурс, який сторінка завантажує під час виконання, стають фактами, які можуть перевіряти правила.
- У звіт потрапляє те, що сторінка втрачає без JavaScript, — її заголовок, опис, канонічне посилання, заголовок першого рівня, внутрішні посилання чи текст, — за порівнянням її сирого HTML із відрендереною сторінкою.

### CSS перевірено так, як його читають браузери

- Таблиці стилів і вбудований CSS розбираються на те, що браузери мовчки відкидають: синтаксичні помилки, через які губиться ціле правило, властивості з помилками в назві та значення поза граматикою властивості.
- Кожен дефект вказує свій рядок і стовпчик — у таблиці стилів або на сторінці з вбудованим блоком.
- Таблиця стилів, яку завантажує кожна сторінка, — це одна знахідка зі сторінками, що її використовують, а вбудований CSS згортається за шаблоном.
- Можливості, яких бракує браузерам, оголошеним у проєкті, перелічуються разом із цими браузерами, а код усередині `@supports` не чіпається.
- Префікси виробників і хаки для старих браузерів ніколи не повідомляються, а для перевірки не потрібен валідатор на Java.

### DNS за кожним просканованим хостом

- Повідомляється про відсутні записи HTTPS, щоб перший візит міг одразу почати з HTTP/3 без зайвого кола для його виявлення.
- CAA перевіряється щодо сертифіката, який сайт справді віддає, тож CA, заборонений у CAA, виявляється ще до того, як зірве поновлення.
- DNSSEC перевіряється від початку до кінця: непідписана зона, слабкі алгоритми, підписи, що перестали оновлюватися, і підписана зона, яку відкидають резолвери з валідацією.
- Сервери імен опитуються напряму, а всі інші запити йдуть лише до вказаного вами резолвера, тож неробочий сервер чи розсинхронізована зона стають видимими, а посилання на піддомен, чий CNAME нікуди не веде, позначається як ризик захоплення.
- Кожне ім’я оцінюється за тим, що його записи кажуть про пошту: від того, що її не використовує, вимагається нульовий MX, SPF, що відхиляє все, і політика DMARC із відхиленням, а від того, що використовує, — один закритий запис SPF і застосована політика DMARC, тож незавершене налаштування видно в обох випадках.
- Реєстрацію домену прочитано з його реєстру, тож продовження за кілька днів, відсутнє блокування передачі або реєстр, що називає інші сервери імен, ніж зона, видно до того, як домен спливе або його заберуть.
- Кожну адресу пов’язано з мережею, що її маршрутизує, тож видно маршрут, який відкидають мережі з перевіркою RPKI, поштовий сервер без відповідного зворотного DNS, або сайт і його сервери імен за одним провайдером.

### Одна знахідка на шаблон, а не на сторінку

- Сторінки групуються за шаблоном URL, тож дефект, спільний для всіх дописів, повідомляється один раз для шаблону допису з прикладами сторінок; дорогі перевірки, як-от доступність, виконуються лише на кількох сторінках кожного шаблону.
- Група, сторінки якої розходяться щодо правила, отримує попередження, що вона, імовірно, поєднує два шаблони.
- Значення, які мають бути унікальними на всьому сайті, як-от заголовки й описи, повідомляються один раз на кожен дублікат з усіма URL, що його мають.
- Кожен запуск завершується кількістю пройдених перевірок і оцінкою від S до F, тож сайти й релізи можна порівняти з першого погляду.

### Іконки завантажено й виміряно

- Кожну іконку, яку називають сторінки, маніфест вебзастосунку та `browserconfig.xml`, завантажують один раз і вимірюють, тож іконка, насправді менша, ніж заявлено, або іншого формату, — це знахідка.
- Favicon, іконку Apple touch, SVG-іконку, закріплену вкладку Safari й плитки Windows оцінюють за тим, чого справді вимагає платформа, як-от непрозорий PNG 180×180 для iOS.
- Сторінку, що не посилається на жодну іконку Apple touch, перевіряють за шляхом, який iOS однаково запитує.

### Вага зображень виміряна, а не оцінена

- Кожне зображення, яке завантажує сайт, перекодовується один раз, і повідомляється, скільки байтів заощадили б AVIF, WebP або щільніше кодування у власному форматі.
- Кожне важке зображення — це одна знахідка зі сторінками, що його використовують, по всьому сайту, а не на вибірці сторінок.
- Зображення, що передають значно більше пікселів, ніж показують, або не мають ширини й висоти для резервування місця, позначаються для кожного шаблону.
- Виміри кешуються разом із зображенням, тож повторний запуск вимірює лише те, що змінилося.
- Шрифти, таблиці стилів і скрипти зважуються так само: шрифти не у WOFF2, шрифти, що ховають текст під час завантаження, і байти, які заощадила б мініфікація.

### Сайт, виміряний цілком

- Вага, запити, час і вуглецевий слід кожної сторінки складаються в показники всього сайту: медіану, 95-й процентиль, крайні значення й суми, навіть коли жодна сторінка не перевищує бюджет.
- Сторінку, значно повільнішу чи важчу за решту або віддану інакше, ніж майже всі інші, буде вказано, і те саме сканування завжди дає ту саму відповідь.
- Усі факти про кожну сторінку експортуються в електронну таблицю без повторного сканування.

### Мертві посилання на сайті й поза ним

- Посилання, що нікуди не веде, на цей сайт чи на інший, — одна знахідка зі списком усіх сторінок, де воно є.
- Посилання на інші сайти перевіряються раз за запуск і запам’ятовуються на тиждень, тож повторний запуск нічого їм не надсилає.
- Сайт, який лише просить перевірку сповільнитися, не вважається мертвим.
- Стрічки, які сторінка оголошує у своєму заголовку, теж обходяться й перевіряються, навіть коли жодне посилання на них не веде.
- Внутрішні посилання з nofollow виявляються, посилання на платний чи користувацький вміст можна перевіряти за політикою rel, яку оголошує власник, а профіль, який сайт називає своїм, але який не посилається назад, як того вимагає верифікація Mastodon, стає знахідкою.

### Автентифікація пошти кожного домену, який він обходить

- Сам визначає, чи домен приймає або надсилає пошту, а для того, що не робить ні того, ні іншого, залишає перевірки без пошти, тож нікому не треба вказувати, який це домен.
- Проходить SPF через кожен include так само, як отримувачі, тож запис, що мовчки ламається через забагато запитів або відсутній include, видно ще до того, як пошта почне повертатися.
- Перевіряє DMARC, DKIM і MX на помилки, за які карають отримувачі: кілька політик, адреси звітів, що їх не приймають, короткі ключі, ключі, залишені в тестовому режимі, і поштові сервери за CNAME.
- Читає MTA-STS, звіти TLS і BIMI від початку до кінця, тож помітить політику, що пропускає поштовий сервер, або логотип, який не покаже жоден поштовий клієнт.
- DANE і жива перевірка STARTTLS кожного поштового сервера доступні, коли їх увімкнути.

### Кожне джерело перевіряється один раз, окрім його сторінок

- Навмисно запитується неіснуюча сторінка, тож хибний 404 або сторінка помилки, що розкриває трасування стека чи версію сервера, — це знахідка.
- Кожен вхід — http чи https, з `www.` чи без, на головну чи вглиб сайту — має вести на одне канонічне джерело постійним перенаправленням, що зберігає шлях, а головна сторінка не повинна перенаправляти відвідувачів за їхньою мовою.
- Файли міждоменної політики, що дозволяють будь-якому іншому сайту читати сторінки із сесією відвідувача, стають знахідкою.
- Плагіни додають власні перевірки для кожного джерела чи хоста; їхні результати використовуються повторно між запусками, а їхні запити ніколи не залишають хост, який вони перевіряють.

### Стрічки, структуровані дані й розмітка перевіряються на кожній сторінці

- Стрічки RSS, Atom і JSON перевіряються на те, на що покладаються читачі стрічок: вони розбираються, називають власну URL-адресу, і кожен запис має незмінний ідентифікатор, тож старий допис ніколи не з’явиться як новий.
- У звіт потрапляють структуровані дані в JSON-LD, Microdata чи RDFa, які не розбираються, не мають того, чого вимагає їхній розширений результат, суперечать сторінці чи решті сайту, містять застарілі терміни schema.org, хибно записані чи суперечливі дати, або чиї хлібні крихти ведуть на відсутні чи переміщені сторінки.
- Маніфест вебзастосунку перевіряється на те, що потрібно для встановлення сайту: назву, стартову сторінку, режим відображення та іконки розмірів, яких просять телефони.
- Розпливчасті тексти посилань на кшталт «натисніть тут» шукаються мовою самої сторінки, а мова без перевіреного списку пропускається, а не оцінюється за англійськими мірками.

### Проблеми швидкості знаходяться без браузера

- Кожна текстова відповідь має стискатися Brotli, Zstandard чи gzip, а кожна сторінка — кешуватися, перевірятися на актуальність і потрапляти в кеш переходів назад і вперед.
- У звіт потрапляють сервер, що досі на HTTP/1.1, сервер, який не оголошує HTTP/3, і сертифікат, чий ключ RSA робить кожне рукостискання більшим, ніж зробив би ключ EC.
- Скрипти й таблиці стилів, що блокують перший рендеринг, відкладене завантаження першого зображення та зображення без розмірів, що тримали б їм місце, знаходяться в HTML кожної сторінки.
- Відрендерені сторінки отримують оцінки Lighthouse за продуктивність, доступність, найкращі практики й SEO та лабораторні LCP, CLS, TBT і FCP на вибірці з кожного шаблону.

### Приватність до згоди

- У звіт потрапляють сторонні й відстежувальні cookies, встановлені під час першого завантаження, ще до будь-якої дії відвідувача, а також вебсховище, записане так само.
- Cookies, які записують скрипти, оцінюються за тими самими вимогами, що й cookies від сервера.
- Постачальники аналітики й реклами, яких завантажує сайт, зводяться в один перелік, тож відомо, кого має назвати політика приватності.
- У звіт потрапляє сторінка без посилання на політику приватності.

### Сайти в будь-якій мережі, обхід без зайвого навантаження

- Onion-сервіси й сайти I2P перевіряються одним налаштуванням, через локальний проксі Tor чи I2P, у темпі й з тайм-аутами, яких потребують ці мережі.
- Кожен запит звичайного обходу й обходу браузером може йти через проксі HTTP, HTTPS чи SOCKS, зокрема через проксі SOCKS, які самі розв’язують імена хостів.
- Сервер, що відповідає «забагато запитів» чи «недоступний», опитується повторно з наростаючою паузою й з урахуванням його `Retry-After`, а ліміт запитів на хвилину тримає обхід у межах, які сайт витримує.
- robots.txt виконується, якщо ви не вкажете інакше.

### Звіти для людей, конвеєрів і агентів програмування

- Знахідки виводяться як текст, JSON, SARIF, Checkstyle, CSV чи HTML-звіт, а збережений обхід переформатовується без повторного звернення до сайту.
- Кожна знахідка може підказати, як її виправити саме на цьому сайті: точний запис, заголовок чи тег із підставленими іменами сайту, а аналіз коду показує ту саму підказку біля кожного сповіщення.
- Формат agent перетворює знахідки на завдання виправлення для агента програмування, впорядковані за серйозністю й за тим, скільки сторінок виправляє кожна правка.
- Дія CI перевіряє сайт на кожен push, завершує завдання з помилкою на обраній серйозності, вивантажує SARIF в аналіз коду й кешує обхід, тож повторна перевірка незміненого сайту майже нічого не коштує.
- Коди виходу відрізняють знахідки від хибної конфігурації та від недосяжного сайту, тож конвеєр знає, що саме не вдалося.

### Залежності сторінок завантажуються один раз

- Скрипти, таблиці стилів, зображення та фрейми, які завантажують сторінки, отримуються один раз за запуск, незалежно від їхнього походження.
- Зламана або небезпечна залежність — це одна знахідка зі списком сторінок, що її використовують, а не знахідка на кожну сторінку.
- Повідомляються скрипти з іншого походження без хешу цілісності та ресурси через звичайний HTTP на сторінках HTTPS.
- Маніфест вебзастосунку завантажується й оцінюється, як будь-яка інша залежність.

### robots.txt читається так, як його читають краулери

- Про robots.txt, що закриває весь сайт для всіх краулерів, повідомляється, бо він прибирає сайт із результатів пошуку.
- ШІ-краулери, яких він називає, перелічуються за призначенням — навчання, пошук чи запит користувача — із позначкою тих, кого він блокує, і назв, яких жоден постачальник уже не надсилає.
- Повідомляється про Content Signals, що кажуть щось інше, ніж yes чи no, для пошуку, входу ШІ або навчання ШІ.

### Понад 500 правил, а нові пишуться як дані

- Правило — це шлях до факту плюс JSON Schema, тож нова перевірка не потребує коду.
- Вбудовані набори охоплюють пошук, заголовки безпеки, TLS, DNS, cookies, продуктивність, доступність, приватність, сталість, посилання, перенаправлення, карти сайту, robots.txt, файли well-known і файли для ШІ-агентів.
- Кожна група URL виконує власні набори правил, а серйозність будь-якого правила можна змінити або вимкнути з командного рядка, середовища чи projectfile.
- axe-core, html-validate і htmlhint працюють у тому самому обході, кожна їхня перевірка — правило, яке можна налаштувати чи вимкнути, як будь-яке інше, а оцінки Lighthouse додаються на відрендерених сторінках.
- Плагіни додають власні факти, правила, набори, формати звітів і джерела URL поряд із вбудованими, а простий список URL можна перевірити окремо.

### Видимість у пошуку перевіряється на всьому сайті

- Заголовки, описи, заголовки розділів, канонічні посилання й теги Open Graph перевіряються на кожній сторінці, а заголовок чи опис, спільний для кількох сторінок, — це одна знахідка з переліком усіх.
- Карта сайту звіряється з обходом: у звіт потрапляють сторінки, які вона перелічує, але на які не посилається жодна сторінка, ті, яких вона не містить, і перелічені сторінки з позначкою noindex.
- У графі посилань усього сайту знаходяться сторінки, що лежать далі ніж за три кліки від стартової, сторінки, які нікуди не посилають, і сторінки, на які посилається лише одна інша.
- Мовні версії мають взаємно називати одна одну й відповідати, а оголошену мову кожної сторінки порівнюють із мовою, якою написано її заголовок і опис.
- Тестову чи робочу копію, відкриту для індексування, виявляють раніше, ніж її знайдуть пошукові системи.

### Заголовки безпеки оцінюються, а не лише виявляються

- Content-Security-Policy читається директива за директивою, із заголовка чи `<meta>`: вбудовані скрипти без nonce чи хешу, `eval`, скрипти з будь-якого хосту та відсутні `object-src`, `base-uri`, `frame-ancestors` чи Trusted Types — кожне окрема знахідка.
- HSTS має тривати досить довго й охоплювати піддомени, а відповіді не мають вгадувати тип вмісту, вбудовуватися в чужі сайти чи розкривати повні URL через referrer.
- Ізоляція між джерелами, Permissions-Policy і точки звітування перевіряються на кожній сторінці, а не лише на головній.
- У звіт потрапляє заголовок X-XSS-Protection, що досі вмикає застарілий фільтр, бо сам цей фільтр можна використати для атаки.
- Заголовок, що порушує власну граматику, як-от max-age у HSTS, що не є числом, чи директива Cache-Control, якої не знає жоден кеш, — це одна знахідка з назвою помилки, а не пропуск через саму наявність і не провал кожної перевірки, що його читає.

### Сервер перевірок

- Той самий образ працює як HTTP API з чергою завдань і як вебсторінка, де будь-хто вводить домен і читає звіт англійською, іспанською чи українською, з JavaScript або без нього.
- Кожна перевірка показує свій поступ під час роботи, її звіт завантажується в усіх форматах, які видає командний рядок, а сайт може показувати свою останню оцінку значком із посиланням на звіт.
- Власник екземпляра задає політики для доменів: заборонити домен верхнього рівня, обмежити частоту перевірок хоста, обмежити сторінки й час і вибрати, які правила можна запускати. Повторний запит у межах заданого вікна повертає вже зроблену перевірку, а кожен клієнт має власний ліміт.
- Політики перечитуються зі змонтованого файлу без перезапуску.
- Перевірку не можна спрямувати на локальні чи приватні адреси або на адреси хмарних метаданих.

### Один обхід — багато перевірок

- Обхід можна зберегти на диску й перевірити знову зі зміненими правилами чи групами без доступу до мережі.
- Перерваний обхід продовжується з місця зупинки.
- Повторний обхід лише питає сайт, чи змінилися сторінка, скрипт або карта сайту, і не завантажує й не аналізує повторно незмінене.
- Бінарні файли оцінюються за заголовками й ніколи не завантажуються повністю, тож посилання на архів чи відео не витрачає трафік.
- Проміжна копія сайту перевіряється як сайт, для якого її зібрано, тож її посилання й карта сайту з адресою продакшену не вважаються помилками.

### Слід кожного перегляду сторінки

- Вуглецевий слід одного перегляду кожної сторінки оцінюється за байтами, які передають сторінка й усе, що вона завантажує, за моделлю Sustainable Web Design, а сторінки понад бюджет потрапляють у звіт.
- carbon.txt сайту має бути присутнім, коректним і актуальним, а розкриття, які він називає, — досяжними.

### Конфігурація TLS, перевірена власними силами

- Перелічуються всі протоколи й набори шифрів, які приймає сервер, зокрема SSLv2, SSLv3, RC4 та експортні, яких сучасні бібліотеки TLS уже не бачать.
- Зламані й слабкі набори, відсутність прямої секретності, короткі прості числа Діффі — Геллмана та стиснення записів є знахідками, як і атаки, які вони відкривають: POODLE, BEAST, SWEET32, FREAK, Logjam, DROWN і CRIME.
- Ланцюжок сертифікатів без проміжних виявляється й на серверах лише з TLS 1.3.
- Власне правило на кшталт «жодних наборів CBC» — це кілька рядків конфігурації, а не код.
- Жоден зовнішній сканер не залучається і нічого не експлуатується: сервер лише питають, що він погодиться узгодити, один раз на джерело, поки результат свіжий.

### Транспорт перевіряється для кожної сторінки, а не для хоста

- Сертифікат, протокол TLS і віддалена адреса зчитуються з з’єднання, яке обслужило кожну сторінку, тож два бекенди за одним ім’ям виявляються, а не ховаються.
- Сертифікати, строк дії яких спливає, відхилені сертифікати, слабкі ключі чи підписи сертифікатів та застарілі версії TLS — це знахідки.
- Час відповіді, ланцюжки перенаправлень і атрибути cookies записуються для кожної сторінки, а значення cookies ніколи не виходять за межі краулера.
- Повідомляється про cookie, яку браузери мовчки відхилять або скоротять, і про попереднє завантаження, яке обіцяє рання підказка, але сторінка потім відкидає.

### Файли, які сайт публікує поруч зі своїми сторінками

- Відсутній або прострочений `security.txt` потрапляє у звіт, тож дослідники безпеки завжди мають спосіб зв’язатися з вами.
- Сайт із полем пароля мусить вести `/.well-known/change-password` кудись, щоб менеджери паролів відправляли користувача прямо до потрібної форми.
- Кожен інший відомий файл (сигнали приватності, метадані OpenID та OAuth, посилання застосунків, відомості про вузол Федивсесвіту, умови для ШІ-краулерів) перевіряється лише тоді, коли він є, тож зламаний файл ніколи не лишиться непоміченим.
- Файли для ШІ-агентів (`llms.txt`, картки агентів, індекси MCP і навичок) перевіряються в окремому пресеті, який вмикається за бажанням, разом із посиланнями в `llms.txt`, що ведуть на зламані сторінки, і наявністю Markdown-версії сторінок.
- Неіснуюча сторінка, віддана як HTML, вважається відсутністю файлу, тож сайт, що відповідає на будь-яку URL-адресу, не засмічує звіт.

## Успадковано від B19 / Ubuntu

### Постійний APT-кеш між збираннями

- Кеші пакетів та індексів APT зберігаються між збираннями через кеш-монтування BuildKit із ключем за серією Ubuntu та архітектурою.
- Повторні збирання використовують уже завантажені пакети замість нового завантаження.
- Необов’язковий LAN-проксі кешування APT, вмикається змінною `M6E_APT_CACHE_HOST`.

### Керування службовими процесами зі спрямуванням журналів (b19-exec)

- Тривалі процеси (демони, сервери) мають stdout і stderr, автоматично спрямовані крізь структурований журналізатор.
- PID служби відстежується для переспрямування сигналів — Docker stop плавно завершує головний процес.
- Рівні журналування для потоків stdout і stderr налаштовуються незалежно один від одного.
- Код виходу служби захоплюється й доступний подальшим хукам.

### Кешовані завантаження артефактів із перевіркою цілісності (b19-fetch)

- Усі зовнішні завантаження проходять крізь трирівневий кеш: локальний каталог `.fetch/`, постійний кеш BuildKit, а потім upstream через aria2c із до 16 з’єднань.
- Необов’язкова перевірка SHA-512 на кожному рівні; невідповідність хеша викликає перехід на наступний рівень, а не збій.
- Режим offgrid повністю блокує всі завантаження та швидко падає з виразною помилкою при промаху кешу.
- Підтримується near-cache-проксі для LAN-збирань, що йдуть через кешувальний проксі.

### Вимірюване виконання команд зі звітуванням про збої (b19-run)

- Будь-яку команду можна обгорнути, щоб отримати автоматичний вимір тривалості та звіт про успіх чи збій.
- Успішний вивід видно лише на вищих рівнях детальності; вивід при збої показується завжди.
- У режимі debug вивід команди транслюється наживо, а не буферизується.

### Одноразова ініціалізація (bootstrap.d)

- Одноразові завдання налаштування (міграції бази даних, створення адміністратора, ініціалізація каталогів) виконуються лише під час першого запуску контейнера.
- Автоматична ідемпотентність: завершені скрипти ніколи не запускаються повторно, навіть між перезапусками контейнера.
- Невдалі скрипти повторюються при наступному запуску; успішні лишаються заблокованими.
- Стан можна скинути очищенням тому, що запускає повний повторний bootstrap.
- Похідні образи додають власні init-скрипти, просто поклавши їх у каталог.

### Модульні хуки збирання (build.d)

- Уся логіка збирання образу живе в пронумерованих shell-скриптах, а не в inline-командах `RUN` Dockerfile.
- Хуки організовано у фази `pre/on/post`, і вони автоматично виявляються за ім’ям етапу, переданим `build-stage`.
- Зарезервована область `always/{pre,post}` обрамляє кожен етап, як би він не називався, тож наскрізне налаштування пишеться один раз, а не для кожного етапу.
- Успадковувані хуки автоматично поширюються на похідні образи через накладання шарів Docker — похідні безкоштовно отримують логіку збирання батька.
- Неуспадковувані хуки вичищаються після виконання, щоб не просочувалися в пізніші етапи.

### Автоматичне визначення кількості CPU (NUMPROCS)

- Доступні CPU визначаються автоматично через downward API Kubernetes, cgroups v2 або резервний `nproc`.
- Виявлена кількість доступна як `NUMPROCS` протягом усього збирання та виконання й використовується для паралельної компіляції, рендерингу шаблонів і запуску тестів.
- Усуває зашиті кількості завдань і гарантує однаковий паралелізм у Docker, Kubernetes і CI.

### Декларативне керування залежностями (b19-deps)

- Метадані зовнішніх залежностей (URL, версія, SHA-512-хеш) зберігаються як прості текстові файли, повністю окремо від скриптів збирання.
- Підтримуються завантаження для конкретних архітектур, багатоверсійні серії та вкладені шляхи компонентів.
- Залежності автоматично виявляються під час розбору Makefile — додайте файли в потрібний каталог, і збирання їх підбере без ручних оголошень.
- `make fetch` завантажує все наперед для офлайн-збирань; підняття версії запускає автоматичний повторний fetch та оновлення хешів.

### Підключована система запуску (entrypoint.d)

- Кожен запуск контейнера проходить крізь послідовність пронумерованих хуків: налаштування сигналів, завантаження секретів, виявлення CPU, перевірка портів, рендеринг шаблонів, bootstrap, старт служби.
- Окремі команди (`docker run img command`) автоматично оминають частину ланцюга запуску та виконуються безпосередньо.
- Окремі хуки чи весь entrypoint можна пропустити під час виконання через змінні середовища, без перебудови образу.
- Похідні образи перевизначають один-єдиний хук (слот 5000), щоб запустити свою службу; решта успадковується.

### Перемикачі функцій для всіх підсистем

- Кожну велику підсистему (entrypoint, healthchecks, bootstrap, тести, секрети, перевірку портів, i18n, shell-хуки) можна вимкнути під час виконання через змінні середовища.
- Окремі хуки entrypoint, bootstrap і перевірок стану можна пропустити за ім’ям, не вимикаючи всю підсистему.
- Перебудова образу не потрібна — перемикачі діють лише в рантаймі.

### Вбудований моніторинг стану (healthcheck.d)

- Перевірка стану у власному для Docker стилі, успадкована всіма похідними образами без додаткової конфігурації.
- Перевірки зовнішнього доступу вмикаються за бажанням: контейнер, який ніколи не звертається до інтернету, не має жодної перевірки, яку може завалити третя сторона, а той, чия робота — інтернет, стає несправним щойно зовнішній світ зникає.
- Працює однаково офлайн і онлайн — перевірки зовнішнього доступу самі вимикаються в режимі offgrid.
- Додати перевірку означає покласти скрипт у каталог, а не писати конфігурацію Docker.

Див. [use-healthcheck.d](../how-to/use-healthcheck.d.md) щодо переліку перевірок, нумерації слотів і налаштувань.

### Багатомовний вивід shell (b19-i18n)

- Усі повідомлення журналу та вивід скриптів, видимі користувачеві, перекладаються через GNU gettext.
- З коробки поставляються англійська, іспанська (`es_CL`) та українська (`uk_UA`).
- Похідні образи автоматично успадковують усі батьківські переклади; перекладати потрібно лише нові чи перевизначені рядки.
- Переклади компілюються під час збирання без накладних витрат у рантаймі.

### Відстеження лініжу образу

- Кожен образ записує свої метадані збирання (namespace, проєкт, версія, базовий образ) у файл лініжу під час збирання.
- Похідні образи зчіплюють лініж зі свого батька, утворюючи повний ланцюг походження від бази до поточного.
- Весь ланцюг лініжу записується в журнал під час запуску (на детальній verbosності, рівень debug) і його можна будь-коли прочитати з файла, тож легко простежити, з чого зібрано запущений контейнер.

### Структуроване журналування з фільтром за рівнем (b19-log)

- Увесь вивід контейнера проходить крізь журналізатор із рівнями й чотирма порогами: error, warn, info, debug.
- Повідомлення нижче налаштованої детальності мовчки відкидаються, тож робочі журнали лишаються чистими.
- Кольори автоматично визначають підтримку терміналу й шанують `NO_COLOR=1`.
- Придатне до конвеєра: вивід команди можна спрямувати крізь журналізатор, щоб застосувати фільтр рівнів і теґи.

### Контейнер без прав root за замовчуванням

- Контейнер працює від користувача без прав root (`ubuntu`, UID/GID 1000), і всі робочі файли належать цьому користувачеві.
- Двоетапне збирання відокремлює системне встановлення від імені root від налаштування середовища виконання на рівні користувача.
- Ідентичність користувача налаштовується під час збирання, а необов’язковий запуск від root переназначає її на користувача хоста, щоб bind-монтування зберігали власника.

### Підтримка ізольованих від інтернету (air-gapped/offline) збирання й виконання

- Єдина змінна середовища (`B19_OFFGRID_MODE=Y`) відтинає весь доступ до інтернету під час збирання та виконання.
- Під час збирання: завантаження блокуються, оновлення APT пропускаються, keyscan SSH пропускається. Усі артефакти мають надходити з рівнів кешу.
- У рантаймі: мережні перевірки стану автоматично пропускаються зі здоровим результатом, тож контейнери лишаються зеленими в ізольованих мережах.
- Списки пакетів APT можна зняти у знімок і вставити для повністю офлайн-збирань образу.
- LAN-служби (кешувальні проксі, реєстри) лишаються досяжними — offgrid блокує інтернет, а не всю мережу.

### Ін’єкція оверлеїв під час виконання

- Файли конфігурації чи даних можна вставити під час запуску контейнера, задавши в `B19_OVERLAY` ім’я каталогу.
- Вміст оверлея рекурсивно копіюється в корінь контейнера, перезаписуючи наявні файли — перебудова образу не потрібна.
- Пропускається в незмінному режимі, що запобігає модифікації під час виконання образів, заблокованих для продакшну.

### Відтворюваний базовий образ (зафіксований за digest)

- Базовий образ Ubuntu зафіксований за SHA-256-digest, а не за тегом, що гарантує детерміновані збирання.
- Підтримуються кілька серій Ubuntu (resolute, noble, jammy) на вибір під час збирання.
- Дзеркала APT налаштовуються окремо за архітектурою для LAN-дзеркал або ізольованих середовищ.

### Перевірка портів

- Усі змінні середовища `*PORT*` перевіряються під час запуску за списком заборонених портів WHATWG і за привілейованими портами (\<1024).
- Завчасно ловить хибні налаштування на кшталт `HTTP_PORT=22`, перш ніж служба непомітно впаде.
- Можна вимкнути під час виконання без перебудови образу.

### Уніфіковане сімейство ранерів життєвого циклу

- Вісім ранерів із пронумерованими хуками покривають повний життєвий цикл контейнера: запуск, healthchecks, тести, bootstrap, хуки збирання, бенчмарки, звіти та shell-сеанси.
- Усі ранери поділяють той самий патерн: покладіть пронумерований скрипт у каталог — він автоматично виявиться й виконається.
- Скрипти з різних шарів образу зливаються — upstream- і downstream-хуки співіснують без конфліктів.
- Кожен ранер має власну семантику збоїв: перервати при помилці (entrypoint, bootstrap), продовжити й порахувати збої (healthchecks, тести), завжди завершуватися успішно (звіти).

### Автозавантаження Docker-секретів (secrets)

- Файли Docker-секретів автоматично виявляються та перетворюються на змінні середовища під час запуску.
- Імена файлів у точковій нотації відповідають змінним середовища у верхньому регістрі (`b19.npm.registry_host` стає `B19_NPM_REGISTRY_HOST`).
- Обов’язкові секрети можна оголосити за ім’ям; контейнер відмовляється стартувати, якщо бракує хоч одного.
- Наявні змінні середовища мають пріоритет над значеннями, похідними від секретів.
- Секрети також доступні в інтерактивних shell-сеансах і healthchecks.
- Не-UTF-8/бінарні секрети (ключі, DER-блоби, gzip-тарболи) **не** експортуються як змінні середовища: Bash обрізає їх на першому NUL, а випадкові байти ламають будь-який інструмент, що читає середовище як UTF-8 (наприклад, `minijinja --env`, яким шаблонізують конфіги). Вони лишаються на диску в `/run/secrets/<name>` для читання як файлів — що й так єдиний правильний спосіб споживати бінарний секрет.

### Хуки інтерактивної shell (shell.d)

- Сеанси `docker exec bash` автоматично завантажують Docker-секрети та будь-які власні хуки, додані похідними образами.
- Хуки зливаються через накладання шарів Docker, тож успадковане та проєктне налаштування shell співіснують.

### Плавна обробка сигналів

- PID 1 — це `tini -g`, який прибирає процеси-зомбі та переспрямовує сигнали всій групі процесів.
- Налаштовуваний набір Unix-сигналів (TERM, INT, HUP, USR1, USR2 тощо) перехоплюється та переспрямовується головному процесу служби.
- `docker stop` чисто завершує службу без осиротілих процесів і втрачених сигналів.

### Шаблони конфігурації Jinja2 (minijinja-cli)

- Рендеринг шаблонів, сумісний із Jinja2, і під час збирання, і під час запуску контейнера.
- Покладіть файл `.j2` будь-де в каталозі застосунку — його виявлено під час збирання й відрендерено при кожному запуску з усіма доступними змінними середовища.
- Рендеринг під час виконання паралельний і автоматичний — похідні образи отримують його без жодної конфігурації.
- Незмінний режим (`B19_IMMUTABLE=Y`) заморожує файлову систему до стану на момент збирання, пропускаючи весь рантайм-рендеринг.

### Вбудований тестовий фреймворк (test.d)

- Тести виконуються всередині запущеного контейнера через `make test` чи `docker exec`.
- Автоматично чекає проходження healthchecks перед виконанням.
- Без залежності від тестового фреймворку — тести це звичайні shell-скрипти з кодами виходу.
- Підтримуються шаблони Jinja2 у тестах, що зручно для перевірки під час виконання значень, зафіксованих під час збирання.
- Продовжує після збоїв і звітує загальну кількість; ніколи не ховає часткові результати.

### Попередньо встановлені службові інструменти

- `mold` як типовий лінкер (можна вимкнути).
- `fd` для пошуку файлів, `minijinja-cli` для рендерингу шаблонів.
- `aria2c` для багатоз’єднаних завантажень, `tini` як PID 1 для прибирання зомбі.
- Інструменти паралельного стиснення: `pbzip2`, `pigz`, `pixz`.
- Інструменти gettext для компіляції i18n, `cURL` для мережевих операцій.

### Шляхи XDG Base Directory

- Стандартні XDG-шляхи (`XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`) задаються в домашньому каталозі застосунку.
- Усі шляхи доступні користувачеві без прав root для запису, без підвищення привілеїв.
